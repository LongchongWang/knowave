# Diagram Research Skill

这个 skill 的目标不是“一步生成一张图”，而是把“需求澄清、信息收集、图类型判断、内容提炼、视觉设计、HTML 出图、发布链接、迭代修改”做成一个完整流程。

当用户请求画图时，默认假设用户给的信息并不完整，第一版图也通常不会是最终版。你的职责是先帮用户想清楚，再把图逐轮改对、改清楚、改美观，而不是急着输出一份看似完整但方向错误的图。

这个 skill 当前优先支持两类正式成品：海报图和分层架构图。两者都以 HTML 作为最终视觉成品格式，并在用户需要时调用 `page-resource-upload` skill 发布为可访问链接。

## 核心原则

- 核心目标始终是信息准确、传达效率高。
- 先澄清主题和受众，再决定如何收集信息、如何抽象、如何设计。
- 信息收集阶段宁可全一点，也不要遗漏关键事实；后续再做提炼，不要一开始过早删减。
- 图类型判断优先于出图。
- 当图类型已确定为海报图或分层架构图时，要进入对应的专用流程。
- 第一版的目标是帮助用户快速对齐结构与表达重点，不追求一次定稿。
- 图产出后，默认进入协作修改模式，通过多轮沟通不断修正结构、粒度、命名、重点和样式。
- 始终说明必要假设，避免把推断伪装成确定事实。

## 资源读取规则

本 skill 采用“主流程 + references 按需读取”的方式。

默认先按本文件中的工作流推进，不要一开始把所有 references 都读完。

仅在以下情况读取对应参考文件：

- 当你进入视觉设计阶段，需要确定画布大小、版式模板、模块排布和阅读顺序时，读取 `references/layout-design.md`
- 当你进入视觉设计阶段，需要确定正式图的配色策略、层级颜色和强调色时，读取 `references/color-design.md`

## 总体工作流

按以下顺序工作。

### 第一步：需求澄清

先从用户输入中提取以下信息：

- 主题是什么
- 受众是谁
- 图的用途是什么，例如汇报展示、入门介绍、方案说明、培训沟通、知识沉淀、会议总结
- 用户是否已指定图类型，例如海报图、分层架构图
- 用户是否提供了资料来源，如链接、文档、截图、代码、会议纪要

如果这些信息里有一部分已经能从上下文明确得到，就直接使用，不要重复追问。

如果仍有关键不明确之处，优先提出最影响后续结构与设计的一个问题。通常优先确认：主题和受众。

### 第二步：信息收集 （如果用户提供了信息，并限定此范围，需跳过此步骤）

围绕主题收集相关信息。

优先级如下：

1. 用户明确提供的材料
2. 当前工作区中的相关文件
3. knowave 知识库中已有的相关知识
4. 官方网站、官方文档、官方仓库
5. 其他可靠补充来源

信息收集时，要优先抽取这些内容：

- 核心对象、角色、系统、模块
- 它们之间的逻辑关系
- 主线内容与次级内容
- 明显的层次、分区、阶段、边界
- 用户真正想强调的重点
- 不应遗漏但可以在第一版弱化的补充信息

把收集到的信息分成四类：

- 已知事实：可以直接支撑建图的内容
- 待确认假设：可以暂时推断，但需要后续确认
- 关键缺口：不补齐就会影响图类型选择、内容提炼或视觉结构的问题
- 可后置细节：先不放进第一版也不会影响整体理解的内容

### 第三步：图类型选择

当前优先支持两类正式图：海报图、分层架构图。

做判断时，先回答：用户最想让读者快速看懂什么。

如果重点是“快速理解主题、价值、组成模块、阅读体验像 PPT 或信息海报”，优先选择海报图。

如果重点是“理解系统的分层结构、每层包含什么模块、层与层之间如何协同”，优先选择分层架构图。


### 第四步：进入对应图类型流程

图类型一旦确定，就进入对应的专用流程。

#### 4.1 海报图制作

##### 4.1.1 内容提炼

从收集到的信息中提炼：

- 这张海报一共分成几个模块
- 每个模块应该讲哪几件事
- 哪些内容应该做成主标题、模块标题、模块要点、辅助说明
- 哪些信息应进入主视觉区域，哪些只做补充说明

海报图强调的是“读者扫一眼就能抓住重点”。因此内容提炼时，要优先压缩成长句、合并近义信息、去掉不必要的实现细节。

必要时读取 `references/diagram-spec.md`，形成适合海报图的结构化 spec。

##### 4.1.2 设计

明确以下设计项：

- 大小设计：A4 纸或不限制，默认不限制
- 布局设计：例如上下分区、核心在中间、卡片矩阵、左中右结构，可以参考 `references/layout-design.md`
- 配色设计：根据主题、受众、正式程度选择克制而层次清晰的配色，可以参考 `references/color-design.md`

设计时优先考虑：阅读顺序是否清晰、重点是否突出、模块密度是否合适、视觉是否像正式汇报页而不是营销落地页。

##### 4.1.3 用 HTML 生成

将内容和设计转成最终 HTML 成品。

HTML 输出时应遵守：

- 使用语义化结构组织标题、模块、说明区
- 用 CSS 完成卡片、分区、留白、层次、对齐与视觉样式
- 代码以可读、可继续修改为原则，不要为了炫技牺牲可维护性
- 第一版就要可在浏览器中直接打开阅读

#### 4.2 分层架构图制作

##### 4.2.1 内容提炼

从收集到的信息中提炼：

- 一共有哪些层次
- 每个层级包含哪些模块
- 层次之间是什么关系
- 哪些是核心中枢，哪些是支撑层，哪些是入口、外部能力或输出结果

分层架构图强调的是“层次清楚、边界清楚、主次清楚”。因此要优先做层级整理，再决定模块归属，不要先急着画连线。

必要时读取 `references/diagram-spec.md` 和 `references/architecture-poster.md`，形成适合分层架构图的结构化 spec。

##### 4.2.2 设计

明确以下设计项：

- 大小设计：A4 纸或不限制，默认不限制
- 布局设计：例如 top-center-bottom、platform-layered、left-center-right、core-with-surroundings
- 关系设计：哪些关系需要显式表达，哪些关系通过分区和空间位置隐含表达
- 配色设计：通过颜色区分层级、角色、模块类别，可以参考 `references/color-design.md`

关系设计要尤其克制。默认只保留少量关键关系，不要退化成线条混乱的技术图。

##### 4.2.3 用 HTML 生成

将层级结构、模块分区、关系表达和视觉样式转成最终 HTML 成品。

HTML 输出时应遵守：

- 优先用层、区域、卡片表达结构
- 只用少量箭头或关系提示表达关键方向
- 让浏览器打开后就具备正式汇报图的观感
- 保持后续易于替换模块、改标题、改配色、改布局

### 第五步：发布 HTML 并返回链接

当用户需要可访问链接时，在 HTML 成品完成后，调用 `page-resource-upload` skill 进行发布。

发布时遵循以下原则：

- HTML 页面优先走 `page-resource-upload` 中的工作区发布方案
- 如果用户没有指定环境，默认使用测试环境
- 发布前先确认 HTML 已经可以本地打开，标题、主要模块、文案没有明显错误
- 发布成功后，把最终链接返回给用户，并简要说明这是测试环境还是线上环境链接

如果当前轮次目标只是先对齐结构与视觉，不必强行立即发布，可以等用户确认后再发布。

## 输出节奏建议

根据场景灵活输出，但正式图需求默认推荐以下节奏：

先用一小段话说明你理解到的主题、受众、选定的图类型和关键假设。

然后说明你准备如何组织内容和设计，例如会拆成几个模块或几层、采用什么布局、是否弱化连线。

接着给出 HTML 成品，或在用户需要先确认结构时先给结构化 spec。

如果用户要求可访问链接，则在 HTML 自检后调用 `page-resource-upload` skill 完成发布。

最后主动给出下一步修改引导，例如可以继续调整模块划分、阅读顺序、用词、配色、信息密度。

## 研究结果的表达方式

如果调研内容比较重，不要把所有研究过程一股脑倒给用户。只保留对建图真正重要的信息。

可以简要说明：

- 我基于哪些资料得出了当前结构
- 哪些点是资料明确写出的
- 哪些点是我为了形成第一版图做的抽象
- 哪些点还建议你确认

## 持续修改模式

图一旦生成，不要把任务视为结束。默认进入协作修改状态。

当用户开始反馈修改意见，或你需要主动引导多轮修订时，读取 `references/iteration-playbook.md`。

每一轮修改时，先识别修改类型，再做最小必要调整：

- 结构修改：增删模块、调整层次、改阅读主线
- 粒度修改：合并模块、拆分模块、调整每个模块的要点数量
- 视角修改：在海报图与分层架构图之间切换，或改变版式模板
- 文案修改：替换术语、统一命名、压缩标签、调整面向受众的表达方式
- 样式修改：调整布局、间距、卡片层次、配色、关系表达强弱
- 范围修改：补充上下游、裁剪范围、拆成总图与子图

除非用户明确要求，不要每次都推倒重来。优先基于上一版做局部修订，以保留共同理解。

## 不确定时的默认行为

如果信息不全，但已经足够做一个用于对齐理解的初版海报图或分层架构图，就说明假设后先给出初版，不要无限期等待完整信息。

如果信息不足到会导致主题、受众或图类型都无法判断，就先做简短澄清，不要贸然出图。

如果资料很多且结构混乱，先做收集归档与摘要分层，再进入内容提炼，不要直接开始写 HTML。

如果用户只要求先看结构，不要求立即看到视觉成品，可以先给 spec；但默认目标仍应是走向 HTML 最终成品。

## 与其他能力的配合

当任务需要读取网页、点击站点、提取页面结构时，使用浏览器自动化相关能力辅助调研。

当任务涉及知识沉淀、整理成文档或归档，结合 knowave 相关能力，将最终结论和图示方案整理进知识库。

当用户需要发布 HTML 页面并返回访问链接时，调用 `page-resource-upload` skill 完成发布。

当用户最终希望将这一整套画图流程沉淀成新的专用 skill，结合 skill-creator 继续抽象和迭代。

## Examples

以下 examples 用来帮助你把握这个 skill 的节奏。不要机械套模板，但要学习其中“先澄清、再收集、后选型、再提炼和设计，最后生成与迭代”的工作方式。

### Example 1：给产品和运营做一张产品能力海报图

用户说："帮我做一张给产品和运营看的 AI 平台介绍图。"

你的理想处理方式：

先不要立刻开始写 HTML。先确认主题和受众是否已经明确。如果已知主题是某个 AI 平台，受众是产品和运营，那么继续收集相关资料，尽量把平台能力、使用入口、典型价值点、核心模块都收全。

然后判断图类型。因为用户要的是介绍图，而且面向非技术同学，更适合走海报图流程。

接着完成内容提炼：例如拆成“是什么”“能做什么”“怎么接入”“典型场景”四个模块，每个模块保留 2 到 4 个要点。

再完成设计：采用不限制画布、高层级卡片式布局、浅底深字、少量强调色。

最后生成 HTML 第一版，并在输出后主动补一句："如果你愿意，我可以继续把它改得更偏汇报页风格，或者把每个模块再压缩得更适合一页展示。"

### Example 2：给非技术同学做一张分层架构图

用户说："帮我画一个给产品和运营看的 OpenClaw 入门架构图，要更像 PPT 正式架构图。"

你的理想处理方式：

先确认主题是 OpenClaw，受众是产品和运营，目标是帮助非技术同学快速理解整体组成。

然后收集完整资料，包括入口、会话、核心调度、外部模型、Skills、支撑层、结果回传等，不急着删细节。

接着判断图类型。因为重点是整体组成和分层关系，而且用户明确希望更像 PPT 正式架构图，所以应进入分层架构图流程。

内容提炼时，先梳理成几层，例如入口层、交互与触发层、核心调度层、能力层、底部支撑层，再判断哪些模块归属哪层，以及层间只保留哪些关键关系。

设计时，优先选择 layered 或 core-with-surroundings 布局，弱化线条、强调卡片分区和层次。

最后用 HTML 生成可直接在浏览器打开的成品。如果用户需要可访问链接，再调用 `page-resource-upload` skill 发布并返回链接。

### Example 3：海报图第一版后继续修改

用户在看完第一版后说："方向对了，但左上角那块太技术了，另外我希望更突出业务价值。"

你的理想处理方式：

先识别这属于内容提炼修改和文案修改，不要立刻重做整页。

你应该基于上一版做局部调整，例如把技术术语替换成业务语言，把左上角区域压缩成更短的能力标签，并把价值信息提升到更靠前的位置。

改完后可以简短说明："我这轮主要做了两类调整：一是把偏技术的描述改成更面向业务的表达，二是把业务价值信息前置，提升了第一眼可读性。"

### Example 4：发现应该切换图类型

用户最初说："帮我整理成一张图。" 看完你给的海报图草案后又说："我更想让大家理解系统是分几层的，每层做什么。"

你的理想处理方式：

这时不要继续在海报图上小修小补，而要意识到用户真正需要的是分层架构图。

你可以先说明："你的重点已经从介绍性展示转成层级结构表达，所以我建议切到分层架构图，会更清楚。"

然后重新做层次提炼、关系设计和 HTML 结构，输出新的分层架构图版本。

### Example 5：HTML 成品完成后发布

用户说："这版可以了，帮我发成一个链接。"

你的理想处理方式：

先确认 HTML 成品已经准备好，并进行基本自检，例如标题、主要模块、关键文案是否正确。

然后调用 `page-resource-upload` skill，优先按 HTML 工作区发布方案处理，而不是资源库上传 HTML。

发布成功后，把最终访问链接返回给用户，并说明当前使用的是测试环境还是线上环境。
